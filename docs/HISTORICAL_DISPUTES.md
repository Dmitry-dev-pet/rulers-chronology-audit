# Реестр исторических противоречий — v1 (исследовательский слой)

**Дата пилота: 13 октября 2026 года.** [Задача #56](https://github.com/Dmitry-dev-pet/rulers-chronology-audit/issues/56), связана с [Wikidata #46](https://github.com/Dmitry-dev-pet/rulers-chronology-audit/issues/46) и [P9 PR #55](https://github.com/Dmitry-dev-pet/rulers-chronology-audit/pull/55).

## Зачем отдельный реестр

Противоречие между текстами источников — **не ошибка кода и не повод переписать историю**. Для исследования полезно одновременно хранить разное:

- **Заявление источника:** что именно он утверждает, с какими исходными календарём, точностью, идентификатором утверждения и качеством ссылок.
- **Объект утверждения:** лицо, юридическая должность, режим/юрисдикция и, если это важно, *конкретное событие* (избрание ≠ коронация ≠ начало срока ≠ прекращение должности ≠ смерть).
- **Уровень расхождения:** две датировки одного периода, подозрение на неверную разметку календарного стиля или неоднозначное соответствие юридических должностей.
- **Статус:** открыт, изучается, разрешён по результатам **документированной человеческой экспертизы**. CI никогда не выбирает исторически «правильную» дату.

Это **другая задача**, нежели 114 оставшихся *не классифицированных* утверждений Wikidata P39. Все начальные кейсы v1 уже имеют известные типы P39, но содержат отдельные нерешённые исследовательские вопросы. Нельзя считать наличие типизированной должности подтверждённым правлением.

## Где истина и где исследовательская гипотеза

| Слой | Роль |
| --- | --- |
| `data/atlas/**` | Действующий Git-источник нормализованной хронологии. **Не изменяется этим PR.** |
| `research/wikidata/p9-office-claims-2026-10-13.json` | Фиксированный список исходных P39-утверждений и их календарных меток (срез 13.10.2026), не заключение эксперта. |
| `research/contradictions/register-v1.json` | **Редактируемый, версионируемый реестр исследовательских вопросов**: по два наблюдения с отдельными источниками, стабильными ID, `comparison_relation` и ручным статусом. |
| `scripts/historical_disputes.py` | Строгая **офлайн-проверка** связей с лицом, должностью, политическим контекстом, каноническими периодами, исходным P39 ID и календарём. Без сети и прав записи. |
| `tests/test_historical_disputes.py` | Контрактные тесты на устойчивость реестра и запрет автоматического переопределения источников. |

Временная SQLite v2, штатная SQLite v1, JSON для Pages, плакат, оригинальная фотография, `provenance.jsonl`, `power_assessments.jsonl`, исторические даты и границы **не меняются**. Реестр **пока не публикуется** на сайте.

## Контракт дат и источников

Каждая дата хранится как объект `{value, precision, calendar, format}`. Например, literal Wikidata `+1598-02-17T00:00:00Z` **с атрибутом** `calendar=gregorian` — именно так заявил внешний источник, даже если пометка спорная. Для пары, подтверждённой независимой справкой, хранятся **два отдельных значения**: `1598-02-17` с `julian` и `1598-02-27` с `gregorian`. Нельзя автоматически вычислить отсутствующий день и выдать его за подтверждённый. Месяцы Шемяки (`1446-02`, `1447-02`) сохраняются с `precision=month`, `calendar=unspecified`.

`wikidata_p39` наблюдение ссылается **на конкретный P39 statement ID**, а не только на QID лица и не на совпавшую фамилию. Валидатор сверяет **Git blob SHA-1 исходного P9-снимка** (`c5b67ad85d4519d1e7d2d280fd7a87b0b29af437`); изменение даже одного байта требует отдельного пересмотра доказательств и версии реестра. Он подтверждает исходный ID, календарь, дату, точность и число внешних references в P9-снимке; связывает канонические ID личности, должности и периода без создания новых записей. У двух граничных случаев Годунова одна P39-запись намеренно встречается **дважды**, но разбираются **разные атрибуты** — начальная и конечная дата.

Институциональная историческая статья — независимое **опубликованное** свидетельство, но не гарантия первичной экспертизы. Ссылки `drive.google.com`, токены доступа, небезопасные URL и пустые источники запрещены. Не допускаются `real_ruler`, неявное приписывание власти и автоматическое снятие противоречий.

## Как вести дальше

1. Зафиксировать **одну проблему** и её единицу сравнения: должность или событие; привязать её к исходному утверждению Wikidata или иному версионированному источнику.
2. Сохранить альтернативное свидетельство отдельно, с оригинальной точностью/календарём и URL на фактически просмотренный источник. Если источники говорят о разных событиях, так и пометить.
3. Оставить `open` или `in_review`, пока исследователь не проверил возможное разрешение. `resolved` допустимо лишь при ручном решении с указанием лица, обоснования и не менее двух источников; даже тогда **никаких автоматических изменений** канонической базы.
4. Только отдельным обсуждаемым PR, если потребуется, сделать **историческую поправку** в каноне, не стирая старые источниковые версии и provenance.

Проверки (Python 3.11+, только стандартная библиотека):

```bash
python3 -m unittest tests.test_historical_disputes -v
python3 -m scripts.historical_disputes --format json
python3 -m scripts.historical_disputes --format markdown
```

**Приёмка:** по-прежнему требуется ручная экспертиза различия «юридическая должность / практическое управление», первичных актов и корректных календарей. Зелёный GitHub Actions доказывает только структурную целостность; он не устанавливает достоверность всех исторических утверждений.

## Биографические разночтения — отдельный адаптер и единая сводка (v2)

Первоначальный `research/contradictions/register-v1.json` **не изменён**: его четыре исторических кейса связаны с неизменным источниковым срезом P9 (по точному Git blob SHA-1). Нельзя искусственно приписывать метрическим записям, биографическим датам или архивным описаниям исходные идентификаторы Wikidata P39.

Поэтому новая версия добавляет **отдельный источник** `research/contradictions/biography-v1.json` и офлайн-проверку `scripts/historical_biographical_disputes.py`. Единая команда `python3 -m scripts.historical_disputes` теперь формирует совокупный отчёт **v2** из обоих проверенных адаптеров: 5 вопросов, 4 персоны, 10 атрибутированных наблюдений. Для просмотра только прежних четырёх используется `--legacy-only`; API `historical_disputes.registry()` для P9 остаётся обратно совместимым.

| Сведения | Дата по старому стилю (Julian) | Дата по новому стилю (Gregorian) | Источник и уровень доверия |
| --- | --- | --- | --- |
| Традиционная опубликованная версия | **11 сентября 1911** | **24 сентября 1911** | `TP309`, [БСЭ](https://www.booksite.ru/fulltext/1/001/008/121/939.htm), запись канона `fact-research-20261010-chernenko-birth-legacy` с `verification=disputed`. Прежняя датировка отдельно подтверждена как традиционная в [сообщении Национальной библиотеки Хакасии](https://nbdrx.ru/arh3470.aspx). |
| Зарегистрированное архивное описание метрики | **18 сентября 1912** | **1 октября 1912** | `TP308`, [Минкультуры Хакасии](https://culture19.ru/contents/587-7-metricheskaya-zapis.html), запись канона `fact-research-20261010-chernenko-birth-archive` с `verification=reference_checked`. Национальный архив Хакасии: **Ф. И-29, оп. 1, д. 142, л. 25 об.–26, запись №32**; включено в реестр 29.05.2026. |

Это не спор о числе дней при конвертации юлианского календаря: **различаются сами годы рождения**. Обе версии уже существовали в `person_facts.jsonl` до этого PR. Более сильное архивное описание ещё не означает, что мы самостоятельно исследовали скан метрической книги; `independent_primary_checked=false`. Статус `open` и `resolution=null` сохраняются.

Ссылка на старую БСЭ уже присутствовала в `sources.jsonl`; её исходная страница не открылась при текущей повторной проверке (403), поэтому нельзя утверждать, что она заново независимо прочитана в этом проходе. Формулировку об устоявшейся версии подтверждает [публикация Национальной библиотеки Хакасии](https://nbdrx.ru/arh3470.aspx). Это отдельно от прямого свидетельства архивного описания и не подменяет его.

### Как валидатор предотвращает подмену фактов

Для биографического источника используются **канонический ID личности, два ID уже существующих фактов и два ID источников** (`TP308`, `TP309`). Каждое наблюдение содержит полную копию *конкретной* записи `person_facts.jsonl` и строки `sources.jsonl` для сверки, старую и новую даты с источниковой точностью, URL, локатор и оговорку. Изменение любой исходной записи или URL без пересмотра кейса приводит к ошибке; **добавление других, не связанных с ним биографических фактов не требует переписывать реестр**.

При совпадении имени, но различии ID, отсутствующем источнике, изменённом годе, ложном повышении `reference_checked` до `primary_checked`, приватной ссылке или попытке автоматически выбрать победителя тесты должны падать. Человеческий статус `resolved` требует имени проверявшего, объяснения и как минимум двух различных публичных источников; разрешение **не переписывает канонический факт**. Цифровой реестр сам по себе не подтверждает достоверность документа.

Новые команды:

```bash
python3 -m unittest tests.test_historical_disputes tests.test_historical_biographical_disputes -v
python3 -m scripts.historical_biographical_disputes
python3 -m scripts.historical_disputes --format json     # Все 5
python3 -m scripts.historical_disputes --legacy-only     # Только исходные 4
```

**Что осталось за пределами версии 2:** другие биографические разногласия и новые виды исторических источников. Они потребуют отдельных явно проверенных адаптеров, а не фиктивных P39-ID или автоматического переноса данных. Статус проверки метрики по оригинальному скану и сопоставление с другими первичными документами остаются человеческим исследованием.
